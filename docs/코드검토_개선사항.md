# 전체 코드 검토 및 개선사항

검토일: 2026-10-27 · 검토 환경: Node v24.15.0 · 기존 코드/문서 수정 없음

## 1. 판단과 범위

**수업 배포 전 경제 거래와 이벤트 진행의 수정이 필요하다.** 기존 검증은 통과하지만, 자산이 근거 없이 늘어나거나 예정된 갈림길이 사라지는 경로를 별도 재현에서 확인했다. 현재 구조를 전면 교체할 필요는 없으며, 거래·이벤트·연간 처리 규칙을 먼저 명확히 하는 편이 좋다.

직접 읽은 코드는 HTML/CSS 2개와 JavaScript 40개, 총 42개 파일·2,995줄이다. `index.html`, `css/`, `js/` 전체, `data/` 전체, `tools/` 전체, `assets/pxl/` 전체와 생성된 `assets/img/sprites.js`를 포함한다. 기획·작업지시·시나리오·경제데이터·에셋가이드, `CLAUDE.md`, `CODING_PLAN.md`, `README.md`, 로컬 명령 파일도 대조했다.

확정 버그, 테스트 도구의 한계, 명세와의 차이를 구분했다. 경제 통계의 외부 출처와 최신성은 이번 검토에서 검증하지 않았다. 기존 파일의 해시 비교에서 변경은 없었고, 최종 `git status --short`에서도 이 보고서만 미추적 파일로 표시됐다.

심각도 기준:

- **P1**: 돈·진행·교육 결과를 바꾸므로 수업 배포 전에 수정.
- **P2**: 특정 조건의 오류, 잘못된 피드백, 검증 공백. 다음 안정화 작업에서 수정.
- **P3**: 유지보수와 문서 정합성 개선.

## 2. 우선 수정할 확정 문제

### R01 · P1 · 저축과 비상금 선택이 자산을 새로 만든다

위치: `data/events-young-data.js:60`, `data/events-young-data.js:62`, `js/effects.js:27`, `js/economy.js:102`.

E11의 예금·비상금 선택은 `asset`만 더하고 현금에서 차감하지 않는다. 연봉은 연말 결산에서 별도로 전액 반영된다. 따라서 같은 월급을 어디에 둘지 정하는 선택이 추가 수입처럼 작동한다.

- 재현: 물가 1, 현금 10에서 E11의 비상금 선택 → 현금 10 유지, 비상금 375, 순자산 **10 → 385**.
- 개선: 외부 수입과 계좌 간 이동을 구분한다. `transfer` 같은 거래로 현금에서 출금하고 예금·비상금에 입금한다. 첫 월급을 선지급한다면 연말 소득과 중복되지 않게 정산한다.
- 완료 기준: 수입·소비·시장 변동 없이 계좌만 옮길 때 순자산이 보존된다. E11 모든 선택지의 자금 출처가 설명된다.

### R02 · P1 · 전세대출 상환분까지 집 구매 자금으로 계산한다

위치: `js/housing.js:31`, `js/housing.js:56`, `js/housing.js:9`.

`buyNeed()`와 `buy()`는 보증금 전액을 사용할 수 있다고 판단한다. 실제 계약 해지에서는 그중 전세대출을 먼저 갚으므로 사용할 수 있는 돈이 더 적다. 선택 가능 검사 후 실행 과정에서 부족분이 신용대출로 자동 전환된다.

- 재현: 중소도시, 현금 0, 전세보증금 12,000, 전세대출 9,600. 가격 40,000인 집을 70% 주담대로 구매하면 `need=0`, 선택 가능, 구매 성공으로 나온다. 실제 결과에는 **주담대 28,000 + 예상하지 못한 신용대출 9,600**이 남는다.
- 개선: 반환 보증금에서 전세대출 상환액을 뺀 금액으로 구매 가능 여부를 계산한다. 검사와 실행이 같은 계산 결과를 사용하고, 자금 부족 시 상태를 바꾸지 않고 실패하도록 한다.
- 완료 기준: 위 조건에서는 자기자금 9,600 부족으로 구매가 막힌다. 부족한 구매 시도 전후 자산·빚이 같다.

### R03 · P1 · 은퇴한 사람에게 취업을 강제한다

위치: `js/events.js:103`, `data/events-young-data.js:152`, `data/events-senior-data.js:42`, `js/effects.js:64`.

퇴직 후 `job=null`인 상태가 실업으로 집계된다. X01에는 연령·은퇴 여부 제한이 없고, 두 선택지가 모두 취업이다. 퇴직금으로 생활하거나 창업 결과를 기다리는 선택을 해도 약 2년 뒤 다시 일해야 한다. X01이 처음 등장했다면 이후에는 `done` 때문에 재발하지 않아, 같은 은퇴 선택도 이전 실업 경험에 따라 다르게 처리된다.

- 재현: 62세, 비부양, 직업 없음, 실업 기간 1년, X01 미경험 → `startYear()` 후 X01 등장. 가능한 선택은 최저임금 일자리/작은 가게 취업뿐이다.
- 영향: 노후 소득·근로 연수·연금과 NPC 결과가 과대 계산될 수 있다. E31 재취업 선택의 기간 소득에 일반 직업 소득이 겹칠 수도 있다.
- 개선: 은퇴·구직·창업 대기 상태를 구분하고 X01을 구직 중인 사람에게만 제안한다. 재취업은 학생이 선택하도록 한다.
- 완료 기준: 은퇴 유지 경로는 80세까지 자동 취업되지 않는다. 재취업 선택만 명시된 소득을 만든다.

### R04 · P1 · 다른 이벤트와 겹치면 침체 갈림길이 사라진다

위치: `js/events.js:47`, `data/events-adult-data.js:49`, `data/events-senior-data.js:39`.

`due()`는 배열에서 먼저 찾은 이벤트 하나를 반환한다. 고정 나이 이벤트는 다음 해로 밀지만 `when` 이벤트는 보류하지 않는다. E21/E30은 침체 당해에만 조건이 참이므로 다른 이벤트가 먼저 나오면 이후에는 열리지 않는다. 시장 폭락은 결산에서 적용되어, 대응 선택 없이 손실만 생긴다.

- 재현: 35세 침체, 지수펀드 보유, E19도 35세 배정 → E19 반환. 36세에는 E21이 나오지 않고 `done.E21=false`로 남는다.
- 개선: 시장 사건의 우선순위를 두거나, 발생 당시 사건과 시장 정보를 보류 큐에 저장한다. 보류된 침체를 보여 줄 때 폭락을 두 번 적용하지 않도록 한다.
- 완료 기준: 투자 자산을 가진 상태로 두 침체를 맞으면 다른 이벤트와 겹쳐도 각각 대응 기회를 얻는다. 폭락은 정확히 한 번 적용된다.

### R05 · P1 · 범위형 이벤트가 조건 충족 전에 영구 종료된다

위치: `js/events.js:52`, `data/events-adult-data.js:33`, `data/events-adult-data.js:65`.

범위 안에서 임의의 한 해를 뽑고, 그해 조건이 안 맞으면 즉시 `done=true`로 만든다. 나중에 범위 안에서 조건이 맞아도 다시 검사하지 않는다. 가족 계획과 학원 이벤트에서 특히 영향이 크다.

- 재현: E20을 30세에 배정, 당시 미혼 → `done.E20=true`. 31세에 결혼해도 가족 계획은 다시 열리지 않는다.
- 개선: 최초 가능 나이부터 마감 나이까지 조건을 재검사한다. 기한 만료와 정상 완료를 별도로 기록하고, 일시적으로 조건이 안 맞는 경우 종료하지 않는다.
- 완료 기준: 30세 미혼 → 31세 결혼이면 38세 이내 가족 계획을 선택할 수 있다. 자녀가 학령기에 도달한 경우에도 같은 검증을 한다.

### R06 · P1 · 운 카드 연속 클릭으로 선택과 보상을 중복 실행할 수 있다

위치: `js/screens/event.js:22`, `js/screens/event.js:33`, `js/screens/event.js:52`.

카드 클릭마다 450ms 타이머를 새로 만든다. 첫 타이머로 열린 선택을 완료해도 남은 타이머가 같은 선택 화면을 다시 연다. 선택 적용과 결과 기록에도 완료 여부 검사가 없다.

- 재현: 화면 노드와 타이머를 대체한 Node 실행에서 R14 카드를 두 번 클릭하고, 첫 선택 완료 뒤 두 번째 타이머를 실행했다. 현금이 **10 → 60 → 110**, 타임라인도 2개가 됐다. 실제 브라우저에서의 연타 속도별 재현은 미검증이다.
- 개선: 첫 뒤집기 때 입력을 잠그고 타이머를 하나만 만든다. 화면 전환 시 예약 작업을 취소하고, 이벤트 해결/다음 단계 콜백을 한 번만 실행하도록 보호한다.
- 완료 기준: 연타·키보드 반복 입력·화면 전환 중 타이머 실행에도 한 이벤트의 효과와 기록은 한 번뿐이다.

## 3. 추가 기능·정확성 개선

### R07 · P2 · 연간 능력치 효과와 확률 효과가 한 해 짧다

위치: `js/screens/year.js:53`, `js/npc.js:73`, `js/effects.js:39`, `js/effects.js:45`, `js/events.js:97`.

현재 연간 능력치 처리는 선택 전에 끝난다. 이후 등록하는 `recurring stat`은 시작 나이가 올해인데 올해 적용은 이미 지나가 있다. `risk`도 그해 `startYear()`가 끝난 뒤 등록하므로 표기 기간보다 추첨 횟수가 한 번 적다. 수입·지출 recurring은 결산에서 처리되어 같은 기간 표기라도 동작이 다르다.

- 재현: 자연 회복률을 0으로 놓고 40세 E24 부업의 건강 -4/년·3년 효과를 적용하면 건강 **70 → 62**로 2회만 감소한다. 의도된 3회라면 58이다.
- 개선: 올해 적용/다음 해 적용을 데이터에 명시하고, 연간 효과 처리 시점을 통일한다. risk도 시작 나이를 저장한다.
- 완료 기준: N년 효과의 실제 적용·추첨 기회가 N회다. 지연 효과와 브라우저/NPC 실행 모두 일치한다.

### R08 · P2 · 결산에 빠진 대출 상환 때문에 표시된 산수가 맞지 않는다

위치: `js/economy.js:132`, `js/economy.js:137`, `js/screens/year.js:64`, `js/lifelog.js:42`.

카드·신용대출 우선 상환액은 `net`에서 빼지만 반환하는 `principal`에는 포함하지 않는다. 화면은 이를 이용해 수입 − 지출 = 남은 돈을 보여 준다.

- 재현: 연봉 3,200, 생활비 1,500, 신용대출 1,000, 시장 금리 조정 0 → 소득 2,720, 이자 70, 반환 원금상환 0, 남은 돈 150. 화면 식은 **2,720 − 1,570 = 150**이 된다. 빠진 1,000이 우선 상환액이다.
- 개선: 정기 상환·추가 상환을 모두 결산 항목에 기록한다. 결산의 상환 전 잉여와 상환 후 잔액을 구분한다. 이벤트 지출도 별도 내역으로 연결하면 좋다.
- 완료 기준: 모든 해에서 표시한 식이 반올림 오차 범위 내에서 성립하고 거래 내역으로 설명된다.

### R09 · P2 · 도시 변경 때 보증금 지원을 다시 받는다

위치: `js/housing.js:23`, `js/housing.js:42`, `js/housing.js:47`, `js/housing.js:87`.

독립 시 부모님 지원을 사용했다는 상태가 없어 재계약마다 같은 금액을 빼 준다. E12에서 월세로 독립한 뒤 E19에서 도시를 바꾸는 실제 경로에서도 지원을 두 번 받는다.

- 재현: 지원 300, 현금 1,000, 중소도시 월세 입주 후 순자산 1,300. 대도시로 변경하면 **1,600**이 된다. 시장 수익 없이 지원 300이 또 생겼다.
- 개선: 지원 잔액 또는 지급 완료 여부를 기록하고 독립 시 한 번만 지급한다.
- 완료 기준: 도시·계약을 바꿔도 누적 지원은 시작 카드의 한도를 넘지 않는다.

### R10 · P2 · 손상된 저장을 정상 데이터로 받아들인다

위치: `js/save.js:26`, `js/main.js:18`, `js/screens/year.js:5`, `js/screens/end.js:7`.

`load()`는 버전과 나이 상한만 검사한다. `{"v":1,"age":30}`도 통과하지만 `marks`, `stats`, `assets` 등이 없어 이어하기에서 예외가 난다. 나이 하한·정수 여부·엔딩의 history 존재도 검사하지 않는다. 저장 실패 역시 호출자에게 알려 주지 않는다.

- 개선: 필수 상태 구조, 유한한 수치, 나이 범위, 배분 합계, 완료 상태의 history를 검증한다. 복구 가능한 누락은 기본값으로 보완하고 나머지는 이어하기를 숨긴다. 쓰기 실패를 반환해 사용자에게 알린다.
- 완료 기준: 빈 JSON·누락 필드·잘못된 숫자·잘못된 버전으로도 타이틀이 정상 동작한다. 정상 저장은 난수 상태까지 동일하게 이어진다.

### R11 · P2 · 하위 선택 결과가 인생 기록에 남지 않는다

위치: `js/screens/event.js:23`, `js/screens/event.js:29`, `js/screens/event.js:34`.

`picked`는 첫 상위 선택 라벨만 저장한다. 근로계약서를 썼는지, 전세보증보험에 들었는지, 결혼식에 얼마를 썼는지, 등록금을 어떻게 냈는지가 타임라인과 인쇄 보고서에서 빠진다.

- 개선: 선택 경로를 배열로 보관하고 상위·하위 선택을 함께 기록한다. 결과 화면·로그·엔딩·인쇄가 같은 기록을 사용하게 한다.
- 완료 기준: E06/E07/E12/E17을 진행한 뒤 구체적인 하위 선택까지 저장·복원·출력된다.

### R12 · P2 · 학자금 대출의 취업 전 이자 처리가 설명과 다르다

위치: `data/events-data.js:118`, `js/economy.js:120`, `js/economy.js:122`.

안내는 취업한 뒤부터 갚는다고 하지만, 코드에서 취업 여부로 제한하는 것은 원금뿐이다. 이자는 재학 중에도 생활자금에서 차감하고, 부족하면 신용대출을 만든다.

- 재현: 물가 1, 일반 지원의 대학 등록금 대출 1,460을 받은 19세 상태를 무수익 시장으로 결산하면, 재학 중 이자가 약 25 발생하고 부족분 약 4가 신용대출이 된다.
- 개선: 게임이 의도하는 거치 기간의 이자 처리 방식을 정하고 안내와 구현을 맞춘다. 실제 대출 제도와의 일치 여부는 별도 확인한다.
- 완료 기준: 재학 중 현금 상환/이자 누적 여부가 화면에 설명되고 동일한 규칙으로 계산된다.

## 4. 검증 도구가 놓치는 문제

### T01 · P2 · 실패를 출력해도 성공 종료할 수 있다

위치: `tools/sim.js:58`, `tools/sim.js:63`, `tools/sim.js:74`, `tools/check-data.js:15`.

시뮬레이션은 오류 개수와 기준 충족 여부를 출력하지만 실패 시 종료 코드를 바꾸지 않는다. NPC 모드는 명시적으로 `process.exit(0)` 한다. 따라서 자동화에서는 회귀를 성공으로 볼 수 있다. 문구 검사도 함수형 본문은 건너뛰며, 기본 상태 하나로만 일부 비용 함수를 평가한다.

개선: NaN·막힌 이벤트·결정성 불일치·NPC 기준 실패를 비정상 종료로 처리한다. 공정/무작위 모드와 실제 4자리 시드도 검사하고, 계좌 이동 보존·연간 횟수·필수 이벤트 보장을 회귀 검사에 추가한다. 함수형 문구는 대표 상태들에서 평가한다.

완료 기준: 고의로 한 검증 조건을 깨면 스크립트가 종료 코드 1을 반환한다. R01~R12의 재현 사례가 재발하면 검사가 실패한다.

### T02 · P2 · 선택지 밸런스 표에 실제로 고르지 못한 실행이 섞인다

위치: `tools/balance.js:25`, `tools/balance.js:45`, `tools/balance.js:51`.

강제할 선택지가 비활성 상태면 다른 선택을 실행해 놓고 해당 선택지 결과 평균에 포함한다. 특히 자금이 필요한 집 구매 결과가 왜곡된다. 또한 다섯 영역을 출력하면서 우열 판정은 `slice(0, 4)`로 실력을 제외한다. 효과 분기의 난수 소비량이 다르면 후속 운 카드 등도 달라져, 주석의 ‘같은 운’까지 보장하지는 못한다.

개선: 실제 강제 선택 성공 여부와 성공 표본 수를 기록하고, 선택 가능한 동일 표본끼리 비교한다. 다섯 영역 전체의 지배 관계를 검사하고 동률·오차 허용 기준을 둔다. 시장 동일성과 이후 개별 운의 차이를 표에 명시한다.

완료 기준: 구매 불가 실행은 구매 선택의 표본에 포함하지 않는다. 선택지별 실제 실행 건수와 제외 건수가 표시된다.

보충: `tools/sim.js:81`의 ‘등장 비율’은 시드별 경험 여부가 아니라 등장 횟수 합계다. 실제 출력에 E17 125%, R02 292%가 나온다. 시드 중 비율과 시드당 평균 횟수를 따로 표시해야 한다. NPC ‘변동 최대’는 표준편차가 아닌 변동계수(CV)로 판정하므로 기준 이름도 맞춰야 한다.

미검증: 크롬·사파리·웨일의 file:// 완주, 태블릿·360px 반응형, 실제 저장 제한 환경, 키보드 전체 경로, 20~30분 플레이 시간, A4 페이지 수, 애니메이션 10% 재생, 실기기 네트워크 요청, 배포 URL. 사용 가능한 브라우저 연결이 없어 이 항목들을 완료로 판정하지 않았다.

## 8. 권장 작업 순서와 완료 조건

1. **회계 거래부터 수정한다 — R01/R02/R08/R09/R12.** 통장 사이에 옮겼을 뿐인데 돈이 늘어나면 이후의 모든 비교가 흔들린다. 거래 전후 순자산 보존과 결산 항목 일치를 먼저 검사한다.
2. **진행 규칙을 수정한다 — R03/R04/R05/R06/R07/R11.** 달력에서 일정이 겹쳤다고 중요한 약속을 지우면 안 된다. 은퇴 상태·이벤트 대기·기간·중복 입력을 정리하고 브라우저/NPC에 같은 규칙을 적용한다.
3. **검증과 수업 화면을 마무리한다 — R10/T01/T02/U01~U05.** 계산기를 고친 뒤 답안지와 화면도 함께 확인해야 한다. 실패 종료 코드, 경로별 회귀 검사, 실제 브라우저 완주·모바일·인쇄를 완료한 후 수치를 조정한다.

기존 시드 난수 분리, DOM 없는 로직, 로컬 에셋과 문구 데이터 분리는 개선을 진행하기에 충분한 기반이다. 기존 검사 통과 결과는 유지하되, 이번에 확인한 회계·진행 조건을 검증 범위에 추가하는 것이 다음 작업의 핵심이다.
